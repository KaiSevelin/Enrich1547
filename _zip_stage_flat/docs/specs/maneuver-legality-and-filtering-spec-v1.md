# Maneuver Legality And Filtering Spec v1

## Purpose

This document defines how `1547Core` decides which maneuvers are currently
legal and which maneuvers should be shown to the player in the HUD.

The goal is to keep the rules rich while keeping player choice surfaces small
and relevant.

## Core Principle

A maneuver may exist in content without being legal in the current window.

The HUD should only surface maneuvers that are both:

- learned by the actor
- legal in the current combat context

## Legality Inputs

Maneuver legality is determined from:

- timing type
- trigger type
- current combat window
- acting side and reacting side
- actor action economy
- current weapon and weapon profile
- weapon traits
- weapon groups
- actor conditions
- actor persistent effects
- battlefield effects
- target state
- range and facing
- available resource costs
- maneuver-specific requirements
- maneuver usage limits

## Timing Gate

The first legality gate is timing.

A maneuver is only legal if its timing type matches the current window:

- `pre` during a declared move or attack before the roll
- `reaction` during a valid reaction window
- `post` during the post-maneuver window for the current attack
- `full-turn` during declaration of a full-turn action

If timing does not match, the maneuver is illegal immediately.

## Trigger Gate

After timing, trigger type must match the current event.

Examples:

- `attack-declared`
- `move-declared`
- `post-attack`
- `damage-taken`
- `threat-zone-entered`
- `charge-declared`

A maneuver with a mismatched trigger is illegal even if its timing type matches.

## Weapon Gate

If a maneuver requires a weapon trait or weapon group, the selected weapon must
match.

Examples:

- `Fast`
- `Shield`
- `Parrying`
- `Bracing`
- `Hooking`
- `Sword`
- `Polearm`
- `Spear`
- `Sidearm`
- `RangedWeapon`
- `Firearm`

If a maneuver has excluded weapon tags, any matching excluded tag makes it
illegal.

## Profile Gate

If legality depends on the selected attack profile, the currently chosen profile
is authoritative.

This matters when:

- a weapon has multiple profiles
- the `main die` matters
- attack mode changes the attack meaningfully

Profile choice is resolved before legality filtering for attached pre-maneuvers.

## Range Gate

If a maneuver depends on distance, current range is part of legality.

Examples:

- ordinary ranged attacks are legal only to `longRange`
- attacks beyond `longRange` need a specific rule that allows `maxRange`
- `Suppressing Fire` may use `maxRange`
- `Volley Fire` may use `maxRange`

## Actor-State Gate

A maneuver is illegal if the actor's current state forbids it.

Examples:

- `Evade` is illegal while locked or prone
- `Subterfuge` skill use is illegal while wearing `Noisy` armor
- a maneuver requiring `hidden` is illegal if the actor is not hidden
- a maneuver requiring mounted use is illegal if the actor is not mounted

## Target-State Gate

A maneuver is illegal if its target requirements are not met.

Examples:

- `Choke` requires the target to already be locked
- `Guard Ally` requires an adjacent ally to be the attack target
- `Formation` requires an adjacent ally with access to `Formation`
- `Lock And Strike` requires the target to already be locked

## Resource Gate

A maneuver is only legal if the actor can currently pay or reserve its cost.

This includes:

- stat-point costs
- `CriticalPoints`
- cost type `null` meaning no resource requirement

For `post` maneuvers, legality must use only the `CriticalPoints` generated by
that current attack resolution.

## Action-Economy Gate

A maneuver is illegal if the actor no longer has the action economy needed to
support it.

Examples:

- full-turn maneuvers require full-turn availability
- movement-attached pre-maneuvers require movement to still be legal
- attack-attached pre-maneuvers require a legal attack declaration

## Usage-Limit Gate

If a maneuver is limited to once per side-based turn:

- it becomes illegal after it has already been used in that side-based turn

Usage tracking should be per maneuver item or per maneuver identity, depending on
content design.

## Filtering Order

The recommended filtering order is:

1. learned content only
2. timing match
3. trigger match
4. actor state match
5. weapon and profile match
6. target-state match
7. resource affordability
8. action-economy availability
9. usage-limit check

This keeps filtering efficient and predictable.

## HUD Rules

The HUD should not show every learned maneuver at all times.

Instead:

- show only currently legal maneuvers for the current window
- hide or disable illegal maneuvers
- group legal maneuvers under the player-facing categories:
  - `Attack`
  - `Defense`
  - `Movement`
  - `Control`
  - `Support`
  - `Special`

## Pre-Maneuver HUD Rules

For a declared attack, the HUD should show only pre-maneuvers that are legal for:

- the current weapon
- the current profile
- the current target
- the current resource state

If multiple legal pre-maneuvers are chosen:

- their effects merge into one pending attack state
- advantage and disadvantage resolve as net `main die` changes

## Reaction HUD Rules

When a reaction window opens:

- interrupt clearly
- show only legal reactions for the reacting side
- make it clear which actor is reacting
- if multiple actors can react, let that side choose which actor uses the window

## Post-Maneuver HUD Rules

For the post-maneuver window:

- show only learned post maneuvers that are currently legal
- filter by:
  - current `CriticalPoints`
  - current weapon
  - current target state
  - current trigger
  - maneuver-specific requirements

Defender legal options appear first.

Attacker legal options appear after defender resolution.

## First Automation Goal

The first legality engine should answer these questions:

- what attacks are legal right now
- which weapon profiles are legal for the chosen attack
- which pre-maneuvers are legal to attach
- which reactions are legal in the current window
- which post-maneuvers are legal for the current `CriticalPoints`

If the system can answer those questions reliably, the rest of combat automation
becomes much easier to build.
